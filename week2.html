Week 2: Security Planning and Testing Methodology

Designing a security baseline and performance testing methodology.

Performance testing plan.


Step Action Tool used Expected result/+ Metric
1)Peperation Installing the necessary tools on Server VM. 'ssh'(from Workstation). 'Sudo apt install htop stress'(on server) The tools are installed and ready to run.
2)MonitoringRemotely connect to the Server VM from the Workstation VM and start the performance monitor. 'ssh ash@192.168.56.10'(on the workstation).(on Server, via SSH) 'htop' is running, showing real-time server stats.
3)Baseline With the server idle (only `htop` running), observe and record the system's normal state. `htop` (on Workstation) **Metric:** Record idle CPU % (e.g., 0-2%), Memory usage (e.g., 250M / 2.0G), and Load Average.
4)Test 1: CPU Load Apply a 1-core CPU stress test for 60 seconds. `stress --cpu 1 --timeout 60s` (on Server) Observe: One CPU core in `htop` will spike to **100%**. The `stress` process will appear at the top of the list.
5)Test 2: Memory Load Apply a 512MB memory stress test for 60 seconds. `stress --vm 1 --vm-bytes 512M --timeout 60s` (on Server) **Observe:** The `htop` memory bar will increase by 512MB. The `stress` process will show high memory usage.
6)Documentation Save screenshots from steps 3, 4, and 5 and note any anomalies (e.g., swap usage, system lag). Screenshot tool. A visual record of the server's performance under baseline, CPU load, and memory load conditions.


Security configuration checklist.


Category Task Configuration Command / Check
SSH Hardening 1) Disable root login 2) (Recommended) Disable password login 3) Restart SSH service Edit '/etc/ssh/sshd_config' and set 'PermitRootLogin no' | Edit `/etc/ssh/sshd_config` and set `PasswordAuthentication no` (Requires setting up SSH keys first) | `sudo systemctl restart sshd`
Firewall 1) Install 'ufw' 2) Deny all incoming traffic 3) Allow all outgoing traffic 4) Allow SSH connections 5) Enable the firewall `sudo systemctl restart sshd` | `sudo apt install ufw` | `sudo ufw default deny incoming` | `sudo ufw default allow outgoing` | `sudo ufw allow ssh` (or `sudo ufw allow 22/tcp`) | `sudo ufw enable` (Type 'y' to proceed)
Mandatory Access Control 1) Check AppArmor status 2) (Action) `sudo aa-status` | Ensure AppArmor is active and profiles are in enforce mode (A default on Ubuntu).
Automatic Updates 1) Install the package 2) Configure for security updates `sudo apt install unattended-upgrades` | `sudo dpkg-reconfigure -plow unattended-upgrades` (Select 'Yes')
User Privileges 1) Confirm root account is locked 2) Review `sudo` group members `sudo passwd -S root` (Should show 'L' for locked) | `getent group sudo` (Should only show your user, e.g., `ash`)
Network Security 1.)Check for open ports 2) (Action) `sudo ss -tulpn` | Verify that the only listening service is `sshd` (port 22). No other ports should be open.

Threat model.


Threat Description Mitigation Strategy
Brute-Force Password Attack If someone tries to log in to the Server VM on the host-only network (e.g. if the Workstation VM has been compromised), they will do so by guessing the admin(me) user's password thousands of times. 1) Disable Password Authentication: Edit '/etc/ssh/sshd_config' on the server to set 'PasswordAuthentication no'. This makes password guessing impossible and forces the use of more secure SSH keys. 2) Firewall: The firewall is set up so that it only allows SSH connections. 3) Install Fail2Ban: Use 'sudo apt install fail2ban' to automatically ban IP addresses that have too many failed login attempts.
Compromised Workstation (Pivot Attack) The 'Workstation VM' would be infected with malware (e.g. from a web browser). The attacker now has a "trusted" position inside the private network to attack the server. 1) Server Firewall (ufw): The server's firewall must be switched on and set up so that it blocks all traffic by default, and only allows SSH (sudo ufw allow ssh). It should not trust the workstation, even though it is on the same network. 2. Least Privilege: The admin(me again) user shouldn't have passwordless 'sudo' access. Requires a SSH key or just a password to login .
VM Escape A sophisticated attacker exploits a security vulnerability in the VirtualBox software itself. This allows them to "escape" the 'Server VM' and gain access to your main Host PC. 1. Host Patching: Keeping the VirtualBox application updated to the latest version. This is the primary defense, as developers patch these vulnerabilities. 2. Guest Patching: Keeping the `Server VM`'s operating system and kernel updated (`sudo apt upgrade`) to patch any vulnerabilities in the guest-level drivers.

Critical reflection.


The second phase was important for understanding Network in Linux. Moving from dynamic (DHCP) to Static IPs was necessary to ensure reliable communication between the Workstation and Server. I had a problem with managing multiple network interfaces (NAT for internet, Host-Only for internal traffic). What went well was SSH into the server for the first time. I understood that the Server VM is not a local machine, but a VM that is a remote resource, simulating a real-world data center environment.
